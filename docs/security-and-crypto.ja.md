# セキュリティと暗号技術

> [English](security-and-crypto.md) | **日本語**

**dfs** は信頼できないインフラを前提とした脅威モデルに基づいて設計されています。ストレージノード（L3 OST）、ロケータレジストリ（L2）、および WebSocket リレーは、能動的な攻撃者によって監視、侵害、または置換される可能性があります。機密性と完全性はクライアント側でエンドツーエンドに強制されます。

---

## 脅威モデル

- **信頼できないストレージとリレー**: L3 OST サーバーおよびリレーは、不透明な `wire_id`（64 文字の 16 進ハッシュ）と AEAD 暗号文のみを参照します。`tree_secret` がなければ、ファイル名、ディレクトリ構造、またはファイル内容を読み取ることはできません。
- **信頼できないネットワーク / MITM**:
  - L2 レジストリエントリ、L1 委任、および L4 リビジョンログは、Ed25519 鍵で暗号学的に署名されます。
  - 直接 TLS OST 接続では、ピン留めされている場合（または L2 `/v1/ost` 経由で通知され、選択されたエンドポイントと一致する場合）、サーバー証明書の SHA-256 フィンガープリント（`ost_cert_sha256`）を検証します。
- **サイレントな鍵ダウングレードの禁止**: 厳格な検証には設定済みの `root_pubkey`（DNSSEC、明示的な `--root-pubkey`、または明示的な `--allow-tofu` 経由）が必要であり、未認証のルートを暗黙的に受け入れることを防ぎます。

---

## 鍵階層

1. **ルート鍵 (L0)**:
   - ドメイン権限（例: `/example.com`）を表す Ed25519 SSH 鍵ペア。
   - L1 委任レコード（`dfs-delegation-v1`）および L2 ロケータレコード（`dfs-l2-locator-v1`）に署名します。
   - DNSSEC `_dfs.<domain>` TXT レコード、明示的な `--root-pubkey` ファイル、または明示的な TOFU 経由で配布されます。
2. **ライター鍵 (L1/L4)**:
   - 特定のサブツリー（例: `/example.com/alice`）への書き込みを L1 委任によって認可された Ed25519 SSH 鍵ペア。
   - L4 ログエントリ（`dfs-l4-log-v1`）、アーカイブ記述子（`dfs-archive-descriptor-v1`）、および立候補レコード（`dfs-candidacy-v1`）に署名します。
3. **ツリーシークレット (`tree_secret`, L3/L4)**:
   - サブツリーのライターおよび認可されたリーダーが共有するシークレット。
   - L2 レジストリや L3 OST サーバーには送信されません。
   - `address_secret` およびチャンクごとの暗号化鍵の導出に使用されます。
   - 文字列シークレットにはバージョン付きの `scrypt-v1` KDF を使用します。明示的な KDF バージョンを持たない設定、招待、およびアーカイブは、既存データの可読性を維持するため従来の SHA-256 導出を保持します。

## 収束 AEAD (`dfs/crypto.py`)

同一サブツリー内でのクライアント側機密性とクロスクライアント重複排除の双方を実現するため、`dfs` は標準プリミティブから構築された収束暗号化（Convergent Encryption）を使用します:

- **圧縮**: 平文ペイロードは、上限付き展開ガードを備えた Zstandard（`dfs/compression.py`）で圧縮されます。
- **決定論的 Plain ID**:
  - `plain_id = HMAC-SHA256(address_secret, b"dfs-plain-id-v1:" + plaintext)`
- **決定論的チャンク鍵**:
  - `chunk_key = HMAC-SHA256(tree_secret, b"dfs-chunk-key-v1:" + plain_id)`
- **認証付き暗号化**:
  - `ChaCha20-Poly1305`（16 バイト認証タグ）がヘッダ/AAD バインディング付きで圧縮ペイロードを暗号化し、チャンクのすり替えや改ざん（`ChunkIntegrityError`）を防止します。
- **コンテンツアドレッシング**:
  - `wire_id = SHA-256(serialized_blob)`（64 文字の小文字 16 進数）。
  - L3 OST サーバーは保存時に `SHA-256(blob) == wire_id` を検証し、クライアントは取得時に `wire_id` と AEAD 完全性の双方を検証します。

## 署名と名前空間

署名は明示的なドメイン分離名前空間を持つ OpenSSH Ed25519（`SSHSIG`）を使用します:

| 名前空間 | 用途 |
|---|---|
| `dfs-delegation-v1` | ルート鍵からライター鍵への L1 サブツリー委任（ローテーション/失効用の `epoch` を含む） |
| `dfs-l2-locator-v1` | 署名付き L2 エンドポイント / ロケータ通知 |
| `dfs-l4-log-v1` | L4 追記専用リビジョンエントリ（`seq`、ルート Merkle チャンク、タイムスタンプ） |
| `dfs-archive-descriptor-v1` | 署名付き `dfscli archive` バンドル記述子 |
| `dfs-candidacy-v1` | 小規模フェイルオーバー/探索用の署名付き立候補レコード |

- 検証は高速なインメモリ `cryptography` 検証と `ssh-keygen -Y verify` フォールバックの双方をサポートします。
- `allowed_signers` インジェクションを防ぐため、制御文字（`\r`、`\n`、`\0`）を含むアイデンティティは拒否されますが、スペースを含む正当なサブツリーパスはサポートされます。

## パス安全性 (`dfs/path_safety.py`, `dfs/crypto.py`)

- パスコンポーネントは UTF-8 NFC に正規化されます。
- `..`、`.`、NUL バイト、コンポーネント内のパス区切り文字、および Windows の予約デバイス名（`CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9`）は拒否されます。
- ローカル具現化およびアーカイブインポート（`dfscli pull`、`dfscli import`）は厳格な包含チェックを強制し、展開されたファイルやシンボリックリンクがターゲットディレクトリ外へ脱出できないようにします。

---

## トランスポートピン留めと Web セキュリティ

- **OST 証明書ピン留め**: `matching_ost_cert_pin` は選択された OST エンドポイントに対して `ost_cert_sha256` を照合し、無関係なエンドポイントへ切り替える際には古いピンをクリアします。
- **Web UI (`dfs/web.py`)**:
  - トークンベースのログイン、HttpOnly セッション Cookie、および IP ごと/グローバルな認証レート制限をサポートします。
  - 読み取り専用 / スコープ付き共有は、設定されたサブツリーへのアクセスを制限します。
